# Raven 1.0.0~beta1

Raven 1.0.0~beta1 arrives eight months after alpha3, and a lot has happened since: raven now compiles OCaml functions over Nx arrays for the GPU.
We've implemented [gpt-oss-20b](https://github.com/raven-ml/raven/tree/main/apps/gpt-oss), OpenAI's open-weight mixture of experts, and it runs as fast as vLLM and llama.cpp!

## From GPT-2 to gpt-oss

Our goal for the first beta was JIT compilation: recording the operations of an OCaml function as a computation graph, and compiling that graph into kernels for a device, be it a CPU or a GPU. We set training GPT-2 on a GPU as the goal post, and met it in July: a GPT-2 training step, from the forward pass to the optimizer's update, compiles into one program and trains on an H100.

We went beyond this. Our compiled gpt-oss-20b decodes and prefills as fast as vLLM and llama.cpp, whose kernels are written by hand. On an RTX 5000 Ada it decodes 124.5 tokens a second, against vLLM's 122.1, and prefills a 512-token prompt as fast as vLLM. [Our gpt-oss post](2026-11-19-gpt-oss-in-ocaml.md) goes into more detail.

## A port of tinygrad

To get there, we ported [tinygrad](https://github.com/tinygrad/tinygrad), an ML compiler written in Python with a strong focus on staying minimal (see our [July blog post](2026-07-08-raven-on-gpus.md)). tinygrad fits raven's general philosophy, and it comes with its own runtimes for NVIDIA and AMD GPUs, which talk to the hardware without the vendor's drivers. That let us extend our goal of depending on no third-party system library to the GPU itself. Our port is distributed as `tolk`, raven's compiler.

## Effects, eager and compiled

nx was designed with JIT compilation in mind from the start, and that design held well. Nx's primitive operations perform an effect, which an effect handler can optionally handle. `rune`, which sits on top of Nx, uses this exact mechanism to implement its function transformations, for instance, `Rune.grad`, already available in alpha3, implements backward automatic differentiation by handling the Nx effects and recording each operation's derivative on a tape, which it then runs backwards.

This lets us write code that reads beautifully:

```ocaml
(* The mean squared error of a linear model with weights w. *)
let loss w = Nx.mean (Nx.square (Nx.sub (Nx.matmul x w) y))

let g = Rune.grad' loss w   (* the gradient, shaped like w *)
```

`Rune.jit` is a new handler in beta1. It handles nx's effects by recording each operation into a computation graph, and hands the final graph to tolk for compilation.

Implementing those as effect handlers also means that transformations compose naturally, for instance:

```ocaml
let grads = Rune.jit' (Rune.vmap' (Rune.grad' loss))

let gs = grads ws   (* ws stacks k models' weights; gs their k gradients *)
```

compiles one program that computes the gradients of k models at once, such as an ensemble trained on the same data. Each transformation handles the effects of the one inside it: `vmap` maps `grad`'s operations, and `jit` compiles what `vmap` produces.

## rig

Unlike tinygrad, raven also computes eagerly: an operation that no handler handles runs right away, on the CPU and, new in beta1, on NVIDIA's Ada GPUs and AMD's RDNA4 GPUs. Other GPUs compute under `Rune.jit`.

Running both eager and compiled code forced an architecture more modular than tinygrad's: the compiled path and the eager path both need a runtime that drives the devices. That runtime is `rig`, a new package in raven to drive devices and run computations on them.

While `rig` started as a direct port of tinygrad's runtime, it evolved independently and its design bears little resemblance to the original. It keeps one thing from tinygrad, though, which is that it needs nothing installed beyond the GPU. It does the work of NVIDIA's `libcuda` and of AMD's runtime itself, in OCaml and C, by talking to the GPU's kernel driver. On Linux it goes further and drives NVIDIA and AMD GPUs over PCI, with no kernel driver at all.

For example, our gpt-oss executable needs no `libcuda` and none of CUDA's libraries: it only loads NVRTC, CUDA's compiler, for compilation. To run the same model, vLLM installs 9.32 GB of Python packages and NVIDIA libraries.

Internally, rig orders work by the memory it touches. CUDA orders work by stream, and leaves the dependencies between streams to the program, as events. rig's interface has neither. Each allocation records, for each device, the last work that wrote it and the last work that used it, and new work waits on exactly those. Because the order lives with the memory, one rule covers everything rig drives: a kernel nx runs eagerly, a program tolk compiled, a read from a file and work on another machine are ordered the same way, with no synchronization layer between eager and compiled code or between devices.

The same records make donation safe. When nx reuses an array's memory for an operation's result, rig hands the memory to the result only if no other array reads it.

Our vision is a static binary that depends on nothing and runs everywhere, driving its GPU itself. Today raven still needs the vendor's compiler, such as NVRTC, to turn a kernel it hasn't cached into machine code. Our 1.0 scope includes ahead-of-time compilation, which will embed the kernels in the binary and remove that last dependency. rig was the hardest part of that vision.

## Devices in the type

The second novelty in beta1, beside compilation, is sharding and remote devices. An nx array can be sharded across several devices, and those devices can be local (the CPU, a file, a GPU) or live on another machine.

An array's type now names the set of devices it lies on. Each set gets a type of its own, so a computation that mixes arrays from two sets fails to build, and moving an array between sets is an explicit `Nx.place`:

```ocaml
let gpu = Result.get_ok (Rig.open_ (Rig_cuda.gpu 0))
module G = (val Nx.devices ~kernels:(module Nx_cuda) [ gpu ])

let x = Nx.ones Nx.float32 [| 1024 |]    (* on the host *)
let y = Nx.place G.on x                  (* a copy on the GPU *)
let z = Nx.add y y                       (* computed on the GPU *)
let _ = Nx.add x y                       (* type error: host and G.d *)
```

Sharding and remote devices are at an early stage. The design is in place, and our focus for the next beta is to exercise it with distributed training and inference, to stabilize it and to bring its performance on par with the leading ML stacks.

## Upgrading

```sh
$ opam install raven
```

beta1 requires OCaml 5.5. Expect to port alpha3 code: [the changelog](../../CHANGES.md) lists, for each package, what changed, starting with the calls that build unchanged and now return other results. The APIs will keep changing until 1.0.

## What's next

We're working towards 1.0, whose goal posts are fine-tuning Llama 3.1 70B and serving it and DeepSeek-V4-Pro, with performance on par with leading ML stacks.
The largest piece of work for this milestone is distributed computing: DeepSeek cannot fit in the memory available on a single node, so its computation is typically distributed over a couple of nodes.

We believe rig is a solid foundation for distributed training and inference in raven, and it already has preliminary support for remote devices, but it needs more work before we can advertise it as an alternative to existing production stacks.

Our work for the next beta release will focus on this: exercising distributed computing, training and inference across GPUs and machines.

Beyond it, our road to 1.0 leads us to implement an inference engine for batched inference at the throughput of the Python stack, from a single static binary.
